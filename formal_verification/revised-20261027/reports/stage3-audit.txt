SRAS Stage 3 audit and minimal modeling recommendations
Scope: independent source audit; recommendations below are not verification results.

Inputs
  Latest paper: the supplied current protocol manuscript (local-only input;
  retained as inputs/main.tex in the complete local ZIP, omitted on GitHub).
  Legacy model: legacy/models/sras-n2.pv (path relative to revised-20261027;
  the line references below refer to this archived snapshot).

1. What the legacy Stage 3 actually checks

  sras-n2.pv:137/183: Stage 3 follows the local Confirm event.
  139-144/185-190: fresh challenge, hardware signature verification, and
  H(challenge, instance-public-key) binding are explicit.
  145-155/191-201: only the measurement identity constraint is checked.
  49-52: TCB requirements and attesting-pair components are explicitly omitted.
  203-214: each honest instance produces only its hard-coded correct measurement.
  217-225: separate akE1/akE2 keys are passed to each verifier; the comments bind
  these keys to the correct measurement in advance. Thus a correctly signed
  but policy-incompatible measurement is not exercised by the default producers.
  147-154/193-200: QuoteSatisfied and CertIssued record measurement and consensus
  policy only. They cannot distinguish two instance keys sharing a measurement,
  different challenges, or which RPE actually performed the successful check.
  78/149/155/195/201: certificate signed payload binds PK_E and PK_RPE, but does
  not include H(pi*).

  Therefore the old Q4 is a correspondence for the modeled measurement check,
  not a proof of full identity/TCB/attester appraisal, certificate-policy binding,
  peer-side certificate validation, or TLS trust establishment.

2. Required paper correspondence

  main.tex:498-505: identity=(measurement, signer, product, security version);
  exact-or-wildcard constraints for the first three; minimum version constraint;
  TCB status membership in the accepted set; invalid/revoked always rejected.
  554-556: conflicting attester assignments or exact constraints yield bottom.
  734: hardware-signed Quote binds instance public key and fresh challenge.
  735-736: designated attester, TCB requirement, and instance identity all checked.
  765-770: signed certificate report binds PK_E, PK_RPE, and H(pi*).

3. Minimal Stage 3 changes recommended to the model author

  Retain the original role structure and the Confirm -> Stage 3 sequence.
  Extend the Quote payload to the standard modeled fields:
      (identity(measurement, signer, product, svn), tcb_status, hchal(n, PK_E)).
  Do not add a new session id or logical entity identifier to protocol messages.
  The target entity E_i is the policy entry selected by the attesting RPE.

  After verifying the signature and challenge/key binding:
      require selected_attester(pi*, E_i) = this RPE;
      require identity satisfies all four joined identity constraints;
      require TCB status is accepted by the joined TCB requirement;
      only then emit QuoteSatisfied and construct/sign the certificate.

  The certificate signed payload should include:
      hcert(PK_E, PK_RPE, hstar(pi*)).
  This is already the paper's certificate structure, not a protocol extension.

  Preserve event names and Q4's correspondence structure, while extending both
  event parameter lists consistently to carry the checked target, key, challenge,
  attributes, issuer and policy, for example:
      QuoteSatisfied(a, E, PK_E, n, id, tcb, pi*)
      CertIssued(a, E, PK_E, n, id, tcb, pi*)
      CertIssued(...) ==> QuoteSatisfied(...).
  These fields are observation metadata, not new wire fields. Including PK_RPE
  or the certificate body is also possible if useful for an auxiliary binding
  query; this should not replace checking the real signed payload construction.
  An auxiliary CertIssued(a,...,pi*) ==> Confirm(a,pi*) can confirm the service
  boundary without changing the original four main property goals.

4. Genuine but non-compliant Quote producers

  A trustworthy hardware signature must not imply policy compliance by design.
  Use a common protected hardware signing root for generic instance processes,
  or explicit diagnostic instance variants, that can have both permitted and
  prohibited actual attributes/TCB statuses.
  An instance generates its own private key internally and quotes its own PK_E
  together with the received challenge. Do not model a trusted quote oracle that
  signs an arbitrary attacker-selected public key as if it originated inside
  a particular enclave.
  The attacker may launch instances with selected actual attributes, relay their
  public keys and challenges, replay Quote messages, and forge under unrelated
  keys. Protected hardware/RPE signing keys remain unavailable to the attacker.
  The Q4 proof concerns appraisal of what the trusted Quote reports; SGX's
  measurement production and vendor collateral processing remain abstract.

5. Finite-domain interpretation

  Exact/wildcard measurement, signer and product checks need explicit values
  sufficient to distinguish a permitted value from a conflicting value.
  A small ordered SVN domain (for example low/high, or three ordered levels)
  suffices to model minimum-version satisfaction and max join in that domain.
  TCB may use a finite valid-status domain and explicit accepted subsets, with
  join as set intersection and empty intersection as bottom. Invalid/revoked
  statuses must have no successful satisfaction rule, even for the weakest
  valid-status requirement.
  Attester assignments use the participant domain; unequal concrete assignments
  for the same entity must fail to join.
  These are finite symbolic appraisal domains, not proofs over every SGX value,
  all vendor TCB statuses, collateral freshness or real cryptographic encodings.

6. Diagnostic negative cases and non-vacuity

  Start from a reachable, compatible two-party initialization. Demonstrate both
  completion and lawful certificate issuance in a common execution.
  For each rejection test also show that the candidate can be submitted/reached,
  so absence of issuance is not solely because Stage 2 never completed.

  - Invalid signature under a disclosed unrelated key: no QuoteSatisfied/issuance.
  - Correct signature but Quote binds a different instance PK: no issuance for
    the request PK; the check must use the same PK later placed in the certificate.
  - Correct signature for another/old challenge: fresh-challenge check rejects.
  - Correct signature and matching key/challenge, but bad measurement, signer,
    product or SVN individually: no certificate for that incompatible instance.
  - Correct identity with policy-disallowed TCB or invalid/revoked TCB: rejected.
  - A satisfiable policy designating another attester for this entity: the wrong
    RPE must not issue, distinct from a conflicting-assignment join abort.
  - Two policies with conflicting attester assignments: join aborts before
    FullJoin/Confirm, rather than reaching Stage 3.
  - Certificate signature payload contains the same PK_E and H(pi*) that were
    successfully checked; no measurement-only correspondence may mask mismatch.

  Prefer small scenario variants or auxiliary observation queries. Do not remove
  attacker message suppression/replay/replacement to make these tests succeed.
  If an unconstrained generic instance role remains in a negative scenario,
  query issuance for the specific bad instance/key or attributes; another honest
  instance receiving a certificate is not a failure of the negative scenario.

7. Explicit boundaries

  Stage 1 authorization is an entry assumption, not newly proved.
  The Stage 3 checks above do not prove that certificate consumers verify the
  issuer mapping/consensus hash correctly unless consumer processes and queries
  are modeled. They do not prove the subsequent TLS exchange.
  A single Stage 2 initialization does not establish cross-initialization replay
  resistance; a fresh Stage 3 challenge only provides its modeled request binding.
  Final reports must distinguish completed checks from these recommendations.

8. Review of the generated revised implementation

  Reviewed sources:
    revised-20261027/generate_models.py
    revised-20261027/models/sras-n2-primary.pv
    revised-20261027/models/sras-n2-auxiliary.pv
    revised-20261027/scenarios/n2-*.pv
  This is a source-level review; consult raw run logs for experimental results.

  Implemented checks agree with the recommended Stage 3 scope:
  - The shared attest process is invoked after each RPE's Confirm event.
  - checksign validates the Quote under the protected common TEE hardware root.
  - teeQuote carries actual Identity and TCB status, and hchal binds the same
    freshly generated challenge and request key used by the verifier.
  - checkentry checks measurement, signer, product, SVN minimum, TCB membership,
    and designated attester. NoAtt does not authorize issuance.
  - QuoteSatisfied is emitted only after all these checks succeed.
  - Both issuance events share (RPE, target entity, RPE key, instance key,
    challenge, actual identity, actual TCB status, consensus policy).
  - hcert binds the instance key, RPE key, and consensus hash; the actual output
    signs that body using the RPE private key.
  - The extra CertIssued argument is the signed BODY, not the signature object.
    The auxiliary correspondence proves body equality and links issuance to
    Confirm, ChallengeSent, and genuine QuoteProduced events. Report this as
    signed-payload binding, rather than an independently modeled consumer-side
    acceptance property.
  - The replicated instance process internally generates its instance key and
    accepts actual attributes/TCB from the attacker. It permits genuine Quotes
    for policy-incompatible instances, unlike the previous fixed good producer.

  The implemented policy/attribute scope is explicit: SVN V0/V1/V2, valid TCB
  statuses Good/Outdated with Both/OnlyGood/OnlyOutdated accepted sets, always
  rejected Revoked/Invalid, symbolic exact-or-wildcard attributes, and 11 chosen
  owner policy profiles. These 11 profiles are not the Cartesian product of all
  finite-field configurations and do not justify claims about every policy.

  Negative Stage 3 sources include individually bad measurement/signer/product/
  SVN, policy-disallowed/outdated TCB, revoked/invalid TCB, another designated
  attester, and an unrelated challenge. The last case models challenge mismatch
  in this single initialization, not arbitrary cross-initialization replay.
  Normal and wrong-attester variants allow generic actual attributes; the other
  bad-attribute variants restrict producers to the selected bad attribute.
  An issuance-unreachability claim is scoped to P1/E1 in these diagnostic files.

  Review suggestions sent to the author:
  - Add wrong-public-key and invalid-signature receiver-check scenarios.
  - In attribute negatives, strengthen preceding-gate non-vacuity with a common
    trace containing Confirm, ChallengeSent(P1,k,n), and QuoteProduced(k,n,id,t),
    instead of relying only on separate Confirm/QuoteProduced reachability tests.
  - Describe fault-injection cases that make an authenticated sender transmit
    a wrong policy/hash as receiver-check diagnostics, not attacker behavior
    possible in the protected honest-RPE main model.
  - A policy-hash-mismatch fixture initially sent Weak while still allowing the
    adversarial owner to declare Weak. The author was notified to fix the
    declaration/payload pair so they are guaranteed different before interpreting
    that fixture's outcome as rejection of a mismatched commitment.
