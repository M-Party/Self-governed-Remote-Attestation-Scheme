SRAS 确认轮诊断：协调性反例及其准确含义

核对范围
  本文只解释 final-v2 中已经运行的结果，不修改模型或增加未运行结论。
  下文日志路径均相对 revised-20261027/results/final-v2/。
  源码路径均相对 revised-20261027/。

一、诊断查询及结果

  两方 D1：
    query kr: pkey, ke: pkey, n: nonce, id: identity, t: tcbstatus,
          x: polstar, body: bitstring;
      event(CertIssued(P1,E1,kr,ke,n,id,t,x,body))
      ==> event(FullJoin(P2,x)).
    源码：models/sras-n2-no-confirm-coordination.pv:281-282。
    完整协议：sras-n2-coordination/output.log:433，is true。
    仅移除确认轮：sras-n2-no-confirm-coordination/output.log:672-673，
      A trace has been found；is false。
    实际耗时：0.24 秒（该诊断模型的整个 ProVerif 调用）。

  三方 D1：
    query x: polstar;
      event(Confirm(P1,x))
      ==> event(FullJoin(P2,x)) && event(FullJoin(P3,x)).
    源码：models/sras-n3-no-confirm-coordination.pv:284-285。
    完整协议：sras-n3-coordination/output.log:420，is true。
    仅移除确认轮：sras-n3-no-confirm-coordination/output.log:697-698，
      A trace has been found；is false。
    实际耗时：0.51 秒（该诊断模型的整个 ProVerif 调用）。

  D1 是解释确认轮作用的辅助诊断，不替代原有 Q1–Q4，也不是新增的
  主安全目标。对应关系要求右侧事件在左侧事件之前已经发生。
  FullJoin 表示对方已收齐、验证并聚合本轮所有必需 policy；它不表示
  对方也已收齐确认消息或已经完成自己的 Confirm。

二、两方原始反例的具体顺序

  日志：sras-n2-no-confirm-coordination/output.log。
  原始图：sras-n2-no-confirm-coordination/graphs/trace1.dot。

  1. 两个 RPE 正常声明策略并发布真实 Evidence Quote。P2 的 owner 选择
     PermissiveRpeTCB；它对 RPE 的 TCB 要求为 Both，而 P1 为 OnlyGood。
     两方实例约束兼容，join 后仍为 OnlyGood。这不是策略冲突场景。
     证据：593-603 行。

  2. 网络交付 P2 的真实 Quote 给 P1。P1 验证后产生 QuotesComplete，
     并发送给 P2 的认证 policy 消息 rho1。网络暂不把该消息交付给 P2。
     证据：605-613 行；rho1 的发送在 613 行。

  3. 网络交付 P1 的真实 Quote 给 P2。P2 验证完成后发送自己的认证
     policy 消息 rho2，然后等待 P1 的 policy。
     证据：615-623 行；P2 的 QuotesComplete 在 619 行。

  4. 网络把 rho2 交付给 P1。P1 的来源、Quote 承诺、policy Self 检查
     均通过，产生 PolicyAccepted、PoliciesComplete 和 FullJoin。
     因该版本没有确认消息交换及等待，P1 紧接着产生 Confirm。
     证据：625-637 行；FullJoin 在 635 行，Confirm 在 637 行。
     在这个消融版本中，保留的 Confirm 名称表示可比较的本地初始化
     完成事件，不表示实际执行过已删除的确认通信。

  5. 一个真实 TEE 以 Identity(mE1,s1,prodA,V1)、Good 状态生成内部密钥。
     P1 收到其公钥，发出 fresh challenge_4；TEE 生成绑定相同公钥和
     challenge_4 的真实硬件 Quote，网络把 Quote 交付给 P1。
     证据：639-659 行；ChallengeSent 在 649 行，QuoteProduced 在 655 行。

  6. P1 通过签名、挑战/公钥绑定和策略检查，产生 QuoteSatisfied 后
     完成 CertIssued。证书签名载荷绑定了同一个实例公钥、P1 公钥以及
     此前聚合得到的 hstar(pi*)。
     证据：661-669 行；QuoteSatisfied 在 667 行，CertIssued 在 669 行。

  至该轨迹终点，P2 尚未收到步骤 2 的 rho1，因此尚未 PoliciesComplete、
  FullJoin 或 Confirm。ProVerif 在 672-673 行重构出可执行反例并报告 D1
  为 false。原始 DOT 图同样只出现 FullJoin(P1)、Confirm(P1) 和 P1 的
  CertIssued：图 188-194 行及 307 行附近；没有 FullJoin(P2) 节点。

  这个反例只需要对真实消息进行选择性交付，没有伪造策略、Quote 或
  证书，也没有让任何 RPE 缩减自己的必需输入集合。P1 已经收齐自己
  的完整输入；P2 尚未收齐自己的输入。

三、三方原始反例的具体顺序及外层标签交换

  日志：sras-n3-no-confirm-coordination/output.log。
  原始图：sras-n3-no-confirm-coordination/graphs/trace1.dot。

  1. P1、P2、P3 正常发布真实 Quotes；P3 选择 PermissiveRpeTCB。
     P1 收到并检查 P2/P3 的真实 Quotes，完成自己的 QuotesComplete，
     向双方发送认证 policy 消息。
     证据：602-636 行；P1 QuotesComplete 在 628 行。

  2. 此次实际重构的轨迹还交换了发给 P2 的 Quote 外层参与方标签：
     P2 在 P1 收集槽收到 P3 的真实 Quote 和 pk(sk3_2)，随后在 P3
     收集槽收到 P1 的真实 Quote 和 pk(sk1_1)。两份 Quote 仍真实有效，
     实际公钥和 policy hash 的硬件绑定没有被修改。
     证据：638-644 行。
     EvidenceChecked(P2,P1,pk(sk3_2),...) 在 640 行；
     EvidenceChecked(P2,P3,pk(sk1_1),...) 在 644 行。
     这是公开外层路由标签可被改写、policy Self 尚待下一阶段核验的
     模型行为；不能把它描述为成功伪造了 P1/P3 的签名身份。

  3. P2 据此向两个实际公钥发送自己的真实签名 policy。发给实际
     pk(sk1_1) 的那份消息原外层标签为 P3，网络将接收方外层标签
     改为 P1 后交付给 P1。内层认证端点本来就是 P1 的真实公钥，
     且发送者签名确为 P2，因此 P1 合法接受 rho2。
     证据：646-662 行；发送在 652-654 行，接收在 656 行，
     PolicyAccepted(P1,P2,...) 在 660 行。

  4. P3 收完 P1/P2 的真实 Quotes，向双方发送 rho3。网络仅把发给
     P1 的 rho3 交付给 P1，没有继续交付让 P2/P3 完成本地聚合所需
     的剩余 policy 消息。
     证据：664-688 行；P3 QuotesComplete 在 672 行，P1 接收 rho3
     在 682 行，PolicyAccepted(P1,P3,...) 在 686 行。

  5. P1 现在确实持有全部三方策略，产生 PoliciesComplete、FullJoin
     和消融版本的 Confirm；P2/P3 均未 FullJoin。
     证据：690-698 行；原始 DOT 图在 397-405 行附近展示 P1 的这些
     事件，未包含 FullJoin(P2) 或 FullJoin(P3)。

  该原始三方图包含外层标签交换，不能伪称它只是简单丢包的图。
  两方原始轨迹已经独立展示了不需要标签交换的选择性交付反例。
  两个反例都没有展示两个已经完成者持有不同 pi*。

四、为何这是协调性差异，而不是 Q1/Q4 违反

  Q1 Agreement 比较两个已经完成的 RPE 的策略。反例终点只有 P1
  完成；它没有展示另一个已完成 RPE 持有不同策略。
  事实上，同批 no-confirm 主查询结果仍为 true：
    sras-n2-no-confirm-primary/output.log:368（Q1）；
    sras-n3-no-confirm-primary/output.log:345（Q1）。

  Q4 Issuance 要求签发对应已通过策略检查的 Quote。两方反例的
  QuoteSatisfied 明确位于 CertIssued 之前，属性符合完整聚合策略，
  公钥、挑战与证书载荷一致。它没有出现违规认证或错误对象签发。
  同批 sras-n2-no-confirm-primary/output.log:518 的 Q4 仍为 true。
  N3 模型不覆盖 Stage 3，不应声称其验证了 Q4。

  真正失去的是：本方开始完成/服务时，对方已经计算出相同结果的
  可验证依据。在完整模型中，每份匹配确认必须由对应受保护 RPE 在
  FullJoin 之后产生，因此本方收到全员确认后，能够建立这些先发生
  的 FullJoin 对应关系；删除该轮后，收到别人的原始 policy 只说明
  对方发送了自己的输入，不说明对方已收到全员输入并完成聚合。

  准确结论：在本轮固定成员、完整输入、确定性规范 join、单次初始化
  和列明有限策略域的模型中，仅删除确认轮仍保持原有 Q1–Q4 的适用
  查询，但会失去上述已计算结果的协调性保证。该结果不能写成
  “移除确认轮导致策略分歧”或“移除确认轮可签发不合规证书”。

  保证边界：D1 的完整协议 true 也不等于所有 RPE 同时完成、同时启动
  服务，或每个对方都已经完成 Confirm。确认消息本身在 FullJoin 后
  就可发出；对方仍可能等待它自己的其他确认。网络任意截留时没有
  活性保证，也没有由本实验推出动态成员或多次初始化的结论。
